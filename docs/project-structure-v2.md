# TaskFlow — Project Structure

The monorepo layout and compose topology, as they actually are.

§1 is generated from the repository tree, so it describes what is on disk rather than what
was planned. Things that are *not* here yet — Kubernetes manifests, ADRs, encrypted secrets,
the per-language `cache/` and `events/` packages — are listed separately in §4 and marked as
absent. If §1 and the filesystem ever disagree, the filesystem is right and this file is a bug.

### 1.1 One workflow, not six

`.github/workflows/ci.yml` is the whole of CI. It has six jobs and they run in this order:

| Job | What it does |
|---|---|
| `validate` | OpenAPI, YAML, shell and Lua lint; migrations up → down → up |
| `migrations` | squawk, against the migration files |
| `changes` | `dorny/paths-filter` — which languages were actually touched |
| `go` / `rust` / `python` / `csharp` / `typescript` | lint + build + test, skipped when untouched |
| `conformance` | boot the stack, run every phase's tests, report per language |
| `security` | gitleaks + trivy, SARIF uploaded |
| `smoke-load` | 30s k6 smoke, so a perf regression surfaces on the PR |

Every `uses:` is pinned to a commit SHA rather than a tag — `make pin-actions` does that, and
`dependabot.yml` keeps the pins fresh. A tag is a mutable pointer, which is exactly how the
March 2025 `tj-actions/changed-files` compromise reached ~23,000 repositories.

### 1.2 Per-language layout

This is the Phase 0 scaffold. Each implementation currently has config, health endpoints, the
response envelope and a healthcheck binary, and nothing else — Phase 1 adds handlers,
repository and service layers to all five.

Every one of the five has the same four files at its root — `Dockerfile`, `.dockerignore`,
`README.md` and its manifest — so only what differs is worth reading.

Three things about that layout are deliberate:

**The healthcheck binary.** Every image is distroless or chiselled, so there is no `curl`, no
`wget` and no shell to run one from. Each language ships a tiny static binary or script whose
only job is to call its own `/health/ready` and exit 0 or 1. C# is the exception — it cannot use
the shared `/healthcheck` path because its check needs an argument, so compose calls
`/app/TaskFlow.Api --healthcheck` instead. That asymmetry is in `docker-compose.yml`, commented.

**Python and TypeScript have a `db` module; Go, Rust and C# do not.** That is scaffolding
noise, not a design decision — the two languages whose driver setup is most fiddly got theirs
written first. Phase 1 gives all five the same shape.

**`migrations/` is not in here.** It sits at the repository root, once. Five copies of the same
schema is a divergence waiting to happen: one copy, one tool (C7).

## 2. Compose Topology

**Three files**, composed as needed. `make up-full` is 18 services — 14 that stay running and
four one-shot init jobs that exit — and several GB of RAM. You will not want all of that while
iterating on one service, which is what the language profiles and `make up-one` are for.

| File | What it holds |
|---|---|
| `docker-compose.yml` | postgres, the migrate job, the five APIs |
| `docker-compose.infra.yml` | valkey, seaweedfs, their init jobs (+ redpanda, behind the `kafka` profile) |
| `docker-compose.observability.yml` | otel-collector, prometheus, loki, tempo, pyroscope, grafana |

They stack rather than replace each other: `make up` is the first two, `make up-full` is all
three. There is no target that starts the observability stack on its own, because it has
nothing to observe.

```bash
# Everything
docker compose -f docker-compose.yml \
               -f docker-compose.infra.yml \
               -f docker-compose.observability.yml up -d --wait    # = make up-full

# Core + infra: what you want 95% of the time
docker compose -f docker-compose.yml -f docker-compose.infra.yml up -d --wait   # = make up

# One language + its dependencies
docker compose -f docker-compose.yml -f docker-compose.infra.yml \
               up -d postgres valkey seaweedfs go-api                # = make up-one IMPL=go

# The optional Kafka appendix, only when you want it
docker compose -f docker-compose.infra.yml --profile kafka up -d
```

`--wait` blocks until every healthcheck passes, which is why every service defines a real
healthcheck rather than the `sleep 30` that CI pipelines accumulate.

### Profiles

Two independent sets of compose profiles are in play, and it is worth keeping them straight.

**Language profiles.** Each API service sits behind a profile named after its language —
`go`, `rust`, `python`, `csharp`, `typescript`. `.env` carries `COMPOSE_PROFILES`, and
`make languages LANGS=go` rewrites that one line. Nothing is deleted; the other four services
simply stop being part of the project, and `check-phase`, `progress`, `status` and `benchmark`
all narrow to match.

**The `kafka` profile.** Redpanda, its console and its topic-init job are the optional appendix
from infrastructure spec §4.9. Phase 6 runs on Valkey Streams — the same container the cache
already needs — so there is no broker in the default stack. Redpanda is ~1 GB of RAM and a 20s
startup you should not pay on every iteration, so it does not start unless you ask:
`--profile kafka`.

## 3. The configuration files themselves

Earlier versions of this document reproduced `docker-compose.yml`,
`docker-compose.infra.yml`, `docker-compose.observability.yml`, `.env.example` and
`.gitignore` in full — about 775 lines of paste.

They are gone, because a copy of a config file is a config file that lies. When the
copies were last checked against the originals, the compose paste was 87% similar and
the `.gitignore` paste 65% similar: both had silently drifted, so anyone reading here
instead of there was reading a fiction with a plausible shape.

Read the files. They are heavily commented, and the comments explain the choices this
document used to narrate:

| File | What its comments cover |
|---|---|
| `docker-compose.yml` | the `x-api-*` anchors, per-language profiles, why the Postgres volume mounts at `/var/lib/postgresql` on 18+, why `migrate` is a job |
| `docker-compose.infra.yml` | Valkey eviction policy vs. event streams, the stream/group init, why the SeaweedFS probe uses `127.0.0.1` |
| `docker-compose.observability.yml` | collector pipeline, why Tempo's OTLP port is not published |
| `.env.example` | every knob all five implementations read, grouped by phase |
| `.gitignore` | why `bin/` is scoped to `csharp/`, and the SOPS negation |

§2 above keeps the parts that are genuinely *about* the topology rather than a copy of
it: the service graph, the profile mechanism and the authoritative port map.

Plus `cmd/outbox-relay/` and `cmd/consumer/` in Phase 6 — both of which can also run in-process,
and deciding which is the interesting part of that phase.

### `k8s/` — not in the roadmap

The roadmap ends at Phase 11. Kubernetes is not part of it, so there are no manifests here. If
you want to take TaskFlow to a cluster as your own extension, the shape that fits is kustomize:

```
k8s/
├── base/                                   # deployment, service, hpa, pdb, networkpolicy
└── overlays/{dev,staging,prod}/
```

Two things already in the repo exist for that day and are worth knowing about:
`SHUTDOWN_PRESTOP_DELAY` (the preStop sleep nobody implements, without which traffic is still
arriving when you stop accepting) and the separate liveness / readiness / startup endpoints.

### `docs/adr/` — architecture decision records

Not present. The decisions the specs argue for — one migration tool, Valkey over Redis, outbox
over direct publish, Valkey Streams over Kafka for Phase 6, SeaweedFS over the archived MinIO —
are currently recorded as prose inside the specs and as comments in the compose files. Extracting
them into numbered ADRs is a genuinely useful exercise, because it forces you to state the
alternative you rejected.

### `secrets/` and `.sops.yaml` — SOPS-encrypted config

Not present. `.gitignore` is already written for it (`secrets/*.yaml` ignored,
`!secrets/*.enc.yaml` negated), so the plumbing is there and the files are not. Dev credentials
in this repo are deliberately plaintext and deliberately worthless — `password`,
`taskflow-dev-secret` — and `make setup` generates a random `JWT_SECRET` locally. There is
nothing here yet that is worth encrypting.
